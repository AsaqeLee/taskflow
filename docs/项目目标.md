# TaskFlow

TaskFlow 是一个面向 Agent 时代的任务协作与工单管理后端，支持 **人-人、人-AI、AI-AI** 的任务流转、协作执行与状态追踪。

它不是一个泛化的“项目管理大全”，而是优先解决：**任务如何在多种执行主体之间被创建、委派、执行、回报、验收和追踪**。

## 系统目标

构建一个统一的任务协作后端，使人类和 AI Agent 都能成为任务参与者，并支持标准化的任务流转与管理。

### 第一阶段目标

第一版先跑通以下闭环：

- 创建任务
- 指派任务给人类或 AI Agent
- 跟踪任务状态变化
- 支持任务委派与撤销
- 保留任务操作记录与责任链

### 这版明确不做

- 复杂项目排期与甘特图
- 高级报表分析
- 即时通信系统
- 多租户复杂权限体系
- 高级自动化工作流编排

## 第一版主场景

第一版优先服务 **人-AI 协作** 场景，即由人类创建并委派任务给 AI Agent，由 Agent 负责执行并提交结果，再由创建者审核验收。

不优先选择人-人协作，是因为现有任务系统已较成熟、差异化不足；不优先选择 AI-AI 协作，是因为第一版验证成本过高、边界不易收敛。

## 当前要解决的问题

传统任务系统默认执行者主要是人，在 Agent 协作场景下会出现以下问题：

1. AI Agent 很难作为正式任务参与者被统一管理
2. 任务执行过程不透明，状态反馈不连续
3. 任务在人类与 AI 之间流转时，责任归属不清晰
4. 失败、阻塞、回滚等情况缺少统一记录机制
5. 任务拆分与继续委派时，链路难以追踪

## 用户角色

系统同时支持自然人和 AI 助手参与协作。

### 系统权限角色

- 超级管理员
- 普通成员

### 任务参与身份

- 创建者
- 委派人
- 负责人
- 执行者
- 协作者
- 观察者
- AI Agent

### Agent 的业务定位

第一版中，Agent 在系统里按 **任务参与者用户** 建模，而不是仅作为被调用的执行资源；但其权限范围与自然人用户不同，后续应在权限设计中单独约束。

## 核心场景

### 场景 1：人类委派任务给 AI
用户创建任务并指派给 Hermes Agent，Agent 接收任务后更新状态、输出结果，用户最终验收。

### 场景 2：人类之间协作与转派
团队成员创建任务后，将任务委派给其他成员执行，并跟踪进展。

在 Day 6 的挑战题推演中，这一场景首先把问题推向了“多人协作 + 负责人权限 + 管理员例外”的关系与权限设计。

但继续推演后，当前更适合 V0 的收缩结论是：
- 第一版先保持 `creator = owner`
- 第一版先保持单执行者闭环，而不是直接支持单任务内多人并发协作
- 如果需要多人参与，更推荐通过子任务拆分来承接，而不是先引入多协作者成员关系与多提交口
- 多人协作不等于多人拥有相同的任务管理权限

### 场景 3：AI 拆分子任务给其他 AI
一个 Agent 接收上层任务后，将子任务继续委派给其他 Agent，并汇总结果回传。

### 场景 4：任务失败后的人工接管
Agent 执行失败或卡住时，任务状态可暴露给人类，由人类重新接管或重新分配。

### 场景 5：查看任务链路与责任归属
管理者可以查看任务从创建到完成经历了哪些委派、由谁执行、在哪一步卡住。

## 核心能力

### 1. 统一任务模型
无论执行者是人类还是 AI Agent，都使用同一套任务模型参与协作。

### 2. 任务生命周期管理
系统支持任务从创建、分配、执行、提交结果、验收完成、撤销到删除的全流程状态管理。

### 3. 多主体委派机制
系统支持任务在人类与 AI Agent 之间流转，并记录委派关系。

### 4. 执行状态回报
第一版默认支持**结果型回报**：执行主体在任务结束后回报完成摘要或失败原因，不强制要求细粒度过程状态流。创建者验收时可附带审核意见或驳回原因。V0 中，任务评论至少包含 `id` 与 `content/comment` 字段；评论回执至少包含 `id`、`creator`、`content/context` 字段。

### 5. 审计与追踪
系统完整记录任务操作日志、责任链路和状态变更历史。

## MVP 功能范围

### 必做功能

- 任务创建
- 任务指派给人类或 AI Agent
- 任务状态流转
- 任务撤销
- 任务删除
- 任务操作日志
- 基础角色与权限
- 任务列表与详情查询接口
- 创建者审核验收机制
- 任务评论 / 回执记录

### 建议第一版补齐的关键机制

- 任务状态枚举
  - `open`
  - `assigned`
  - `in_progress`
  - `submitted`
  - `approved`
  - `completed`
  - `cancelled`
  - `deleted`
- 执行反馈机制
  - completion summary
  - failure reason
  - review note
- 评论 / 回执机制
  - task comment: `id`, `content/comment`
  - comment receipt: `id`, `creator`, `content/context`
  - execution comment
  - rejection comment
  - review comment
- 状态规则补充
  - `submitted` 表示执行者已提交结果，等待 owner 审核
  - `approve` 与 `close` 在 Day 6 / Day 7 中被正式拆开：先认可结果，再正式关闭任务
  - `approved` 是 `approve` 的正式状态落点，`close` 再把任务推进到 `completed`
  - `reject` 是对 `submitted` 的审核结论；驳回后任务回到 `assigned`，再由执行者重新 `start`
  - `approve` 后如需反悔，应先撤销 `approve`，再回到 `submitted` 做下一步判断
  - 被撤销任务重新激活后回到 `open`
- 委派链
  - parent task / child task
  - from actor / to actor
- 参与者类型
  - human
  - ai_agent
- 子任务机制
  - 第一版允许任务拆分为子任务，但默认由创建者发起
  - 执行者如需拆分，应以建议形式提出并由创建者确认

## 状态流转与责任规则（V0）

### `open -> assigned`
- V0 暂定仅由创建者触发。
- 后续版本可再评估是否向管理员开放。

### `assigned -> in_progress`
- 仅由执行者触发。
- 该规则强调：一个执行状态在同一时刻应由单一执行者持有并推进。

### `in_progress -> submitted`
- 由执行者触发。
- 当执行者为 Agent 时，Agent 可以自行提交 `submitted`，因为第一版将 Agent 视为正式系统成员与任务参与者。

### `submitted -> approved`
- 由 owner 触发。
- 表示 owner 已认可当前提交结果，但任务尚未正式结束。
- 这个状态的价值在于保留 `approve` 与 `close` 的动作差异，也为后续“撤销 approve -> 回到 submitted”提供明确落点。

### `approved -> completed`
- 由 owner 触发。
- `close` 是正式收尾动作，任务在这一刻进入最终完成态。
- 如果创建者与 owner 是同一人，则这条闭环最简单；当前 V0 先采用这种简化。

### `submitted -> assigned`
- 由 owner 触发。
- 表示 owner 对提交结果做出驳回判断，并要求当前执行者继续完善。
- Day 7 已进一步定稿：驳回后任务回到 `assigned`，而不是直接回到 `in_progress`，这样能保留 `start` 的动作语义。

### `assigned / in_progress / submitted -> cancelled`
- 由创建者触发。
- 用于终止当前执行流程，但保留任务及其历史记录。

### `cancelled -> open`
- 由创建者触发。
- 表示重新激活任务，并将任务恢复到待重新分配状态。

### 关于多人协作与负责人闭环的补充说明
- Day 6 挑战题先把问题推向了“负责人、协作者、管理员、多人协作”的关系建模。
- 但继续推演后，当前 V0 更适合的简化结论是：
  - `creator = owner`
  - 维持单执行者闭环
  - 不在 V0 直接支持单任务内多人并发协作
- 如果确实需要多人参与，更推荐通过子任务拆分来承接，而不是先引入协作者关系表、主提交人、多入口状态推进等更重的抽象。

## 权限边界（V0）

### 关闭任务
- 当前 V0 简化版里，仅 owner 可关闭任务。
- `close` 不应被理解为 owner 可以在任意阶段随意使用的动作，而应是 `approve` 之后的正式收尾动作。

### 回滚状态
- `admin rollback` 在 Day 6 推演后决定暂不进入 V0。
- 如果 owner 在 `approve` 后、`close` 前反悔，更适合通过“撤销 approve -> 回到 submitted -> 再判断 approve / reject”的方式处理，而不是引入泛化的回滚动作。

### 删除任务
- 允许创建者删除自己创建的任务。
- 允许管理员删除任务。

### 撤销任务
- V0 仅允许创建者撤销任务。

### 查看评论 / 回执
- V0 仅允许创建者与执行者查看任务评论 / 回执。

### 创建任务
- V0 仅允许自然人用户创建任务。
- Agent 在第一版中作为系统成员参与执行，但不负责主动创建任务。
- 后续版本可再评估逐步向 Agent 开放更完整权限。

### 重新指派
- V0 不允许执行者自行将任务重新指派给其他人。
- 如需变更执行者，应由创建者重新分配。

## 如果第一版只能保留 4 个核心功能

优先保留：

1. 任务创建
2. 任务指派
3. 任务状态更新
4. 任务操作记录 / 审计日志

## 非功能需求

- 第一版以纯后端 API 为主，不包含完整前端界面
- 界面与交互体验要求留待后续版本定义
- 系统需要支持清晰的状态可视化能力（即使初期仅通过接口返回体现）
- 关键操作需要保留可审计记录
- 数据模型需要为后续 Agent 协作扩展预留空间

## 待进一步确认的问题

1. Agent 在第一版里需要独立登录与认证能力，但首版交互可以先以 API 调用为主。
2. 删除默认采用逻辑删除，并对创建者开放；是否进一步限制到管理员仍可后续再收紧。
3. 第一版暂不对 Agent 可见任务范围做额外限制。
4. Day 5 / 实现阶段需要继续判断：哪些写操作需要同时写入 `TaskRecord` 与 `AuditLog`。
5. Day 5 / API 设计阶段需要继续收敛：动作型接口的最小集合、哪些动作需要请求体，以及哪些动作必须按完整业务动作整体处理。

## V0 数据模型草案

### 设计原则
- 先按业务对象和业务关系建模，再进入数据库实现细节。
- V0 优先满足可实现性与可扩展性的平衡，避免过早做过细拆分。
- `Task` 承载任务本体，`TaskRecord` 承载协作正文，`AuditLog` 承载关键动作留痕，`User` 作为基础主体对象被引用。
- 先把最小字段集收稳，再进入可空性、枚举值、索引和 DDL 设计。

### 1. User
用于表达系统中的基础主体，包括自然人与 Agent。

最小字段：
- `id`
- `name`
- `type`
- `created_at`
- `updated_at`

说明：
- `type` 在 V0 用于区分 `human` 与 `agent`。
- 创建者、执行者等不是独立对象，而是 `User` 在任务上下文中的角色。

### 2. Task
用于保存任务本体。

最小字段：
- `id`
- `title`
- `description`
- `status`
- `creator_id`
- `assignee_id`
- `created_at`
- `updated_at`

说明：
- `creator_id` 表达任务稳定归属。
- `assignee_id` 在 V0 用于表达当前执行者，先服务于单执行者闭环。
- Day 3 先不把 `creator_name`、`assignee_name` 这类展示信息混入任务对象，而是通过引用 `User` 表达关系。
- `parent_task_id`、`deleted_at` 等字段可以作为 Day 4 继续评估是否纳入数据库化表达的扩展项，但不进入当前 Day 3 最小字段集。

### 3. TaskRecord
用于统一承载评论、执行说明、审核说明、驳回说明等协作正文。

最小字段：
- `id`
- `task_id`
- `author_id`
- `type`
- `content`
- `created_at`

说明：
- 这张对象 / 表在 V0 统一承载评论与回执类记录。
- `type` 在 V0 至少需要覆盖：`comment`、`execution_receipt`、`review_receipt`、`rejection_receipt`、`failure_receipt`。
- `TaskRecord` 负责承载正文内容，而不是系统动作留痕。

### 4. AuditLog
用于保存系统级关键动作留痕。

最小字段：
- `id`
- `task_id`
- `actor_id`
- `action`
- `created_at`

说明：
- `AuditLog` 只负责记录关键动作，不承载大段协作正文。
- `from_status`、`to_status`、`metadata` 在后续很可能有价值，但 Day 3 暂不纳入最小字段集。
- `action` 在 V0 可覆盖：`task_created`、`task_assigned`、`task_started`、`task_submitted`、`task_approved`、`task_rejected`、`task_closed`、`task_cancelled`、`task_reopened`、`task_deleted`。

### V0 核心对象关系（Day 3 收敛）
- `Task.creator_id -> User.id`
- `Task.assignee_id -> User.id`
- `TaskRecord.task_id -> Task.id`
- `TaskRecord.author_id -> User.id`
- `AuditLog.task_id -> Task.id`
- `AuditLog.actor_id -> User.id`

说明：
- `Task` 是当前 V0 的关系中心对象。
- `User` 是被多个对象共同引用的基础主体。
- `TaskRecord` 与 `AuditLog` 都围绕 `Task` 展开，但职责不同：前者负责协作正文，后者负责动作留痕。
- Day 3 已明确应该用“关联 / 引用”表达对象关系，而不是把其他对象的展示字段直接“包含”进当前对象。

### V0 推荐方案总结
如果当前目标是“尽快跑通，同时保留未来演进空间”，建议采用：
- `User`：统一表达自然人与 Agent 两类主体
- `Task`：承载任务本体与最基本归属 / 执行关系
- `TaskRecord`：统一承载评论与回执正文，用 `type` 区分语义
- `AuditLog`：独立保存系统级关键动作留痕

这套方案的核心是：
- 先稳住 4 个核心对象，而不是过早引入更多中间关系对象
- 不把评论 / 回执 / 审计日志塞进任务主表
- 不把对象字段和对象关系混在一起
- 先完成业务字段与关系建模，再进入数据库实现层

## V0 功能模块拆解

### V0 功能模块分层

#### 1. 核心闭环模块
- 任务管理
- 任务分配与执行流转

#### 2. 核心配套模块
- 任务协作记录

#### 3. 轻量支撑模块
- 审计追踪（V0 要有，但先做轻）

### 模块职责边界

#### 任务管理
负责：
- 创建任务
- 查看任务列表
- 查看任务详情
- 修改任务基本信息
- 删除任务（逻辑删除）

V0 中，“修改任务基本信息”先只包含：
- 标题
- 描述

任务管理模块暂不负责：
- 分配执行者
- 状态流转
- 执行提交
- 验收 / 驳回
- 评论 / 回执
- 审计日志

#### 任务分配与执行流转
负责：
- 指派给人或 Agent
- 开始执行
- 提交结果
- 验收通过 / 驳回
- 推动状态变化

V0 最小能力建议：
- 分配任务
- 开始执行
- 提交结果
- 验收通过
- 驳回退回

说明：
- 这组能力已经足以跑通“创建者分配 -> 执行者执行 -> 执行者提交 -> 创建者验收 / 驳回”的核心闭环。
- `驳回退回` 的业务含义是：创建者拒绝当前提交结果，并将任务退回到可继续执行的状态。
- `取消任务`、`重新激活`、`重新分配执行者` 虽然在整体规则中存在，但不必先并入该模块的最小能力定义，可作为 V0 次级能力保留。

#### 任务协作记录
负责：
- 普通评论
- 执行说明
- 驳回原因
- 审核说明

V0 最小能力建议：
- 普通评论
- 执行说明
- 驳回说明
- 审核说明

说明：
- 这四类记录已经足以承载 V0 中最关键的协作文本。
- `执行说明` 负责说明执行者做了什么、提交了什么结果。
- `驳回说明` 负责说明为什么当前提交未被通过，以及需要如何继续完善。
- `审核说明` 负责说明创建者通过验收时的判断或补充意见。
- 若后续发现普通评论使用频率很低，也可以继续压缩到“只保留回执型记录”，但当前 V0 先保留这四类更稳妥。

#### 审计追踪
负责：
- 记录关键操作
- 记录状态变化
- 保留责任链

V0 最小能力建议：
- 记录任务创建
- 记录任务分配
- 记录开始执行
- 记录提交结果
- 记录验收通过
- 记录驳回退回
- 记录删除任务

说明：
- `任务创建` 应记录，因为它是整个任务生命周期的起点。
- `任务分配` 必须记录，因为责任归属发生了变化，需要知道任务被分配给了谁。
- `开始执行` 建议记录，因为它可以保留任务真正进入执行阶段的时间点。
- `提交结果` 应记录，因为它标记了执行者已完成当前轮次提交，进入待验收阶段。
- `验收通过` 应记录，因为它标记任务闭环完成。
- `驳回退回` 必须记录，因为它代表一次关键审核判断，并直接影响后续流转。
- `删除任务` 应记录，因为即便采用逻辑删除，也需要保留任务被删除的痕迹。

V0 中该模块应保留，但不追求复杂审计分析能力。

### 审计记录的最小信息（当前收敛）
以“分配任务”为例，至少需要包含：
- `task_id`
- `executor_id` / `to_actor_id`
- `operator_id` / `actor_id`
- `created_at`

说明：
- `task_id` 用来明确这条记录属于哪个任务。
- `executor_id` / `to_actor_id` 用来明确任务被分配给了谁。
- `operator_id` / `actor_id` 用来明确是谁执行了这次分配动作。
- `created_at` 用来明确这次分配发生在什么时候。

如果缺少 `operator_id`，就无法知道是谁完成了这次分配；如果缺少 `created_at`，就无法还原责任链的时间顺序。

以“提交结果”为例，至少需要包含：
- `task_id`
- `actor_id` / `executor_id`
- `created_at`
- `record_id` / `submission_record_id`

说明：
- `task_id` 用来明确是哪个任务进入了提交阶段。
- `actor_id` / `executor_id` 用来明确是哪位执行者提交了结果。
- `created_at` 用来明确提交发生的时间。
- `record_id` / `submission_record_id` 用来指向对应的执行说明 / 回执正文。

当前判断倾向采用 **方式 B**：
- 执行摘要正文优先放在协作记录 / 回执中。
- 审计日志负责记录“谁在什么时候对哪个任务做了什么”，并保留对正文记录的引用。
- 这样可以保持职责更清晰：审计负责留痕，协作记录负责承载正文内容。

如果缺少对正文记录的引用，审计日志就只能说明“提交过”，但无法回到那次提交的实际内容。

以“驳回退回”为例，至少需要包含：
- `task_id`
- `actor_id` / `operator_id`
- `target_record_id` / `submission_record_id`
- `created_at`
- `reason_record_id` / `review_record_id`

说明：
- `task_id` 用来明确是哪个任务发生了驳回。
- `actor_id` / `operator_id` 用来明确是谁做出了驳回判断。
- `target_record_id` / `submission_record_id` 用来明确驳回的是哪一次提交。
- `created_at` 用来明确驳回发生的时间。
- `reason_record_id` / `review_record_id` 用来指向对应的驳回说明正文。

如果缺少“驳回的是哪一次提交”的信息，后续就无法把审核判断和具体提交结果对应起来；如果缺少原因正文的引用，就无法解释为什么会被退回。

### 审计记录的通用骨架 vs 事件特有信息（当前收敛）

通用都要有的：
- `task_id`
- `actor_id`
- `created_at`
- `event_type`

说明：
- `task_id`：明确这条审计记录属于哪个任务。
- `actor_id`：明确是谁执行了这次动作。这里更准确的是“操作者 / 动作发起者”，而不是固定写成创建者或执行者，因为不同事件的操作者不同。
- `created_at`：明确动作发生的时间。
- `event_type`：明确这条记录到底是“分配任务”“提交结果”“验收通过”还是“驳回退回”。

某些事件才需要的：
- `to_actor_id` / `executor_id`：分配任务时，用来表示分配给谁。
- `target_record_id` / `submission_record_id`：提交结果或驳回退回时，用来表示对应的提交记录。
- `reason_record_id` / `review_record_id`：驳回退回时，用来引用驳回说明正文。

当前判断：
- `创建者`、`执行者` 更适合作为特定业务上下文中的角色概念，而不是所有审计记录都必须具备的固定通用字段。
- 更稳定的通用字段应该是：任务、操作者、时间、事件类型。
- 提交内容、驳回内容属于事件特有信息，不应强行提升为所有审计记录的通用字段。

## 业务规则 vs 接口 / 对象设计（当前收敛）

### 更偏业务规则的内容
- 任务如何流转：如分配、开始执行、提交结果、验收通过、驳回退回。
- 谁可以触发哪些动作：如创建者负责分配、验收、驳回，执行者负责开始执行、提交结果。
- 驳回的业务含义：不是长期状态，而是一次审核判断，任务退回到可继续执行状态。
- 哪些协作文本必须存在：如提交结果需要执行说明，驳回需要驳回说明。

### 更偏接口 / 对象设计的内容
- 任务管理模块需要哪些最小能力：创建任务、任务列表、任务详情、修改任务基本信息、逻辑删除。
- 任务分配与执行流转模块需要哪些最小能力：分配任务、开始执行、提交结果、验收通过、驳回退回。
- 任务协作记录模块需要哪些最小能力：普通评论、执行说明、驳回说明、审核说明。
- 审计追踪模块需要记录哪些关键事件，以及每类事件最小需要哪些信息。
- 审计日志与协作记录之间如何分工：正文放在协作记录，审计负责留痕与引用。

### 当前判断
- `任务流转` 确实是最核心的业务规则之一。
- `审计` 本身更像支撑系统可信运行的能力，不是主业务规则；但“哪些关键动作必须留痕”依然属于重要的系统规则。
- 换句话说：审计不是主业务流程本身，但它是对业务流程的追踪与约束机制。

## 从模块走向对象 / 接口（当前收敛）

### 你的当前判断
- 任务管理更容易落到对象层
- 审计追踪更容易落到对象层
- 任务流转更容易落到接口 / 动作层

### 这个判断为什么大体正确
- `任务管理` 围绕的是 `Task` 这个核心对象，天然适合先从对象视角理解：任务是什么、有哪些基本信息、允许做哪些基本管理动作。
- `审计追踪` 虽然是支撑模块，但最终也会沉淀成相对稳定的 `AuditLog` 对象，因此也适合从对象视角理解。
- `任务流转` 的重点不是“它长什么样”，而是“谁在什么条件下触发什么动作，并把任务推进到哪里”，所以它天然更接近接口 / 动作设计。

### 但还要再加一层更精确的理解
- `任务管理`：**对象为主，接口围绕对象展开**。
- `审计追踪`：**对象为主，但更多是系统内部沉淀对象，不一定先暴露复杂操作接口**。
- `任务流转`：**规则和接口为主，但它依然依附于 Task 这个对象，而不是脱离对象独立存在**。
- `User`：**更像被多个对象共同引用的基础主体对象**，而不是这轮 V0 里优先单独展开的业务主对象。
- `Participant`：**V0 当前判断下可以先不单独作为对象存在**；若只是表达“某个 User 在某个 Task 中扮演创建者/执行者等角色”，当前可先由 `Task` 上的归属字段与业务规则承载。

### 关于 `Participant` 是否需要单独存在的当前判断
- 当前倾向：**V0 暂时没有必要单独引入 `Participant` 对象。**
- 原因：
  - 目前 V0 的参与关系还比较简单，核心只收敛到创建者、执行者，以及评论/审计中的动作发起者。
  - 如果现阶段没有多执行者、多观察者、多审核者、成员订阅、参与历史等复杂需求，单独再抽一层 `Participant` 容易过度设计。
  - 现阶段更稳妥的做法是：先让 `User` 作为基础主体对象，由 `Task`、`TaskRecord`、`AuditLog` 直接引用，并通过字段和规则表达角色含义。
- 这也意味着：
  - `creator`、`executor` 先作为 **Task 上的业务角色字段 / 语义** 理解。
  - `comment creator`、`audit actor` 则由记录对象直接引用 `User`。
- 后续只有在出现以下场景时，再考虑引入 `Participant` / `task_participants`：
  - 一个任务需要多个执行者
  - 需要观察者 / 审核者 / 委派者等多种并存角色
  - 需要记录参与关系历史
  - 需要把“任务参与关系”本身当成可查询、可管理对象
### 当前更稳的表达方式
- `Task`：核心业务对象。
- `AuditLog`：支撑型对象。
- `TaskRecord`：协作记录对象。
- `任务流转`：围绕 `Task` 发生的一组状态推进接口 / 动作，而不是一个独立对象。
- `User` / `Actor`：参与协作的主体对象，是 `Task`、`TaskRecord`、`AuditLog` 背后的发起者、执行者、审核者与被分配者来源。

### V0 对象清单（当前定稿）
- `User`
- `Task`
- `TaskRecord`
- `AuditLog`

当前判断：
- **V0 先收敛为这 4 类对象即可。**
- `User`：基础主体对象，被其他对象引用。
- `Task`：核心业务对象。
- `TaskRecord`：协作记录对象，承载评论、执行说明、驳回说明、审核说明。
- `AuditLog`：审计留痕对象，记录关键动作与责任链。
- `Participant`：V0 暂不单独引入，避免过度设计。

### V0 对象关系（当前收敛）
- `Task` 关联 `User`：用于表达任务创建者、当前执行者等主体关系。
- `TaskRecord` 关联 `Task`：用于表达这条协作记录属于哪个任务。
- `TaskRecord` 关联 `User`：用于表达是谁写下了评论、执行说明、驳回说明或审核说明。
- `AuditLog` 关联 `Task`：用于表达这条审计记录属于哪个任务。
- `AuditLog` 关联 `User`：用于表达是谁触发了这次关键动作。

当前理解：
- `Task` 是关系中心对象。
- `User` 是基础主体对象，被 `Task`、`TaskRecord`、`AuditLog` 共同引用。
- `TaskRecord` 和 `AuditLog` 都围绕 `Task` 展开，但职责不同：
  - `TaskRecord` 负责承载协作文本与回执内容。
  - `AuditLog` 负责承载关键动作留痕与责任链。

### 关于 `User` / `Actor` 是否缺失的当前判断
- **是，前面的“核心对象清单”如果只写 `Task`、`TaskRecord`、`AuditLog`，会少掉参与主体这一层。**
- 但 `User` / `Actor` 和 `Task` 的角色不同：
  - `Task` 是系统要管理的核心业务对象。
  - `User` / `Actor` 是让这些业务动作发生的参与主体对象。
- 因此更准确的分法不是“只有三个对象”，而是：
  - **核心业务对象**：`Task`
  - **协作/留痕对象**：`TaskRecord`、`AuditLog`
  - **参与主体对象**：`User` / `Actor`
- 如果后续继续收敛到实现层，还要进一步回答：
  - V0 是直接用 `User` 同时承载 human / agent，还是抽象出更上层的 `Actor` 概念。
- 结合当前 V0 目标，比较稳妥的理解是：
  - **先把人和 Agent 都视为可参与任务的主体**；
  - 数据层可以先用 `User` + `type`（human / agent）表达；
  - 如果后续协作类型变复杂，再上升为更抽象的 `Actor` 模型。

### 这一步最重要的认知
- 不是所有模块都应该先落成“对象”。
- 有些模块更适合先定义“对象”，有些模块更适合先定义“动作 / 接口”。
- 但动作 / 接口最终仍然要挂靠在对象之上，不能脱离对象语境独立设计。
