# TaskFlow V0 模块与职责边界（Day 2 / Day 3 对齐版）

> 来源：`docs/项目目标.md`
> 目标：把 TaskFlow 当前 V0 的模块划分、职责边界，以及它们与核心对象的对应关系单独沉淀出来，方便后续进入接口设计与代码分层。

## 文档目的

这份文档不是在重复 PRD，而是在回答三个更工程化的问题：
1. V0 到底有哪些模块？
2. 每个模块分别负责什么、不负责什么？
3. 这些模块分别围绕哪些核心对象展开？

---

## V0 功能模块分层

### 1. 核心闭环模块
- 任务管理
- 任务分配与执行流转

### 2. 核心配套模块
- 任务协作记录

### 3. 轻量支撑模块
- 审计追踪

---

## 模块职责边界

### 1. 任务管理

**负责**
- 创建任务
- 查看任务列表
- 查看任务详情
- 修改任务基本信息
- 删除任务（逻辑删除）

**V0 中任务管理先只修改**
- 标题
- 描述

**暂不负责**
- 分配执行者
- 状态流转
- 执行提交
- 验收 / 驳回
- 评论 / 回执
- 审计日志

**主要围绕的对象**
- `Task`
- `User`（通过 `creator_id` / `assignee_id` 被引用）

### 2. 任务分配与执行流转

**负责**
- 指派给人或 Agent
- 开始执行
- 提交结果
- 验收通过 / 驳回
- 推动状态变化

**V0 最小能力建议**
- 分配任务
- 开始执行
- 提交结果
- 验收通过
- 驳回退回

**说明**
- 这组能力已经足以跑通“创建者分配 -> 执行者执行 -> 执行者提交 -> 创建者验收 / 驳回”的核心闭环。
- `驳回退回` 的业务含义是：创建者拒绝当前提交结果，并将任务退回到可继续执行的状态。
- `取消任务`、`重新激活`、`重新分配执行者` 虽然在整体规则中存在，但不必先并入该模块的最小能力定义，可作为 V0 次级能力保留。

**主要围绕的对象**
- `Task`
- `User`
- `AuditLog`（记录关键动作）
- `TaskRecord`（与提交 / 审核说明联动，但不承载状态机本身）

### 3. 任务协作记录

**负责**
- 普通评论
- 执行说明
- 驳回原因
- 审核说明

**V0 最小能力建议**
- 普通评论
- 执行说明
- 驳回说明
- 审核说明

**说明**
- 这四类记录已经足以承载 V0 中最关键的协作文本。
- `执行说明` 负责说明执行者做了什么、提交了什么结果。
- `驳回说明` 负责说明为什么当前提交未被通过，以及需要如何继续完善。
- `审核说明` 负责说明创建者通过验收时的判断或补充意见。
- 若后续发现普通评论使用频率很低，也可以继续压缩到“只保留回执型记录”，但当前 V0 先保留这四类更稳妥。

**主要围绕的对象**
- `TaskRecord`
- `Task`
- `User`

### 4. 审计追踪

**负责**
- 记录关键操作
- 记录状态变化
- 保留责任链

**V0 最小能力建议**
- 记录任务创建
- 记录任务分配
- 记录开始执行
- 记录提交结果
- 记录验收通过
- 记录驳回退回
- 记录删除任务

**说明**
- `任务创建` 应记录，因为它是整个任务生命周期的起点。
- `任务分配` 必须记录，因为责任归属发生了变化，需要知道任务被分配给了谁。
- `开始执行` 建议记录，因为它可以保留任务真正进入执行阶段的时间点。
- `提交结果` 应记录，因为它标记了执行者已完成当前轮次提交，进入待验收阶段。
- `验收通过` 应记录，因为它标记任务闭环完成。
- `驳回退回` 必须记录，因为它代表一次关键审核判断，并直接影响后续流转。
- `删除任务` 应记录，因为即便采用逻辑删除，也需要保留任务被删除的痕迹。
- V0 中该模块应保留，但不追求复杂审计分析能力。

**主要围绕的对象**
- `AuditLog`
- `Task`
- `User`

## 模块与核心对象的对应关系

### `Task`
主要服务于：
- 任务管理
- 任务分配与执行流转

### `TaskRecord`
主要服务于：
- 任务协作记录
- 部分配合执行流转（如提交说明、审核说明、驳回说明）

### `AuditLog`
主要服务于：
- 审计追踪
- 任务分配与执行流转中的关键动作留痕

### `User`
主要服务于：
- 所有模块的主体引用
- 创建者 / 执行者 / 操作者等上下文身份表达

## Day 3 之后需要统一的认识

- 模块不等于对象。
- 模块也不等于接口。
- 一个模块可能围绕一个对象展开，也可能围绕多个对象共同协作。
- `Task`、`TaskRecord`、`AuditLog` 是对象层；
  `任务管理`、`执行流转`、`协作记录`、`审计追踪` 是模块层。
- 后续做 API 设计时，应该让接口服务模块职责，而不是机械按对象生成 CRUD。

## Day 5 第一轮补充结论（动作型接口边界）

### 通用更新 vs 业务动作
- `Task` 的通用信息修改，V0 先只开放 `title`、`description`。
- `status`、`assignee_id` 不应由客户端通过通用 patch 直接修改。
- 原因不是字段不能改，而是它们背后承载了业务流转、责任归属变化、权限判断与审计留痕。

### V0 更适合的动作型接口集合
- `POST /tasks/{id}/assign`
- `POST /tasks/{id}/start`
- `POST /tasks/{id}/submit`
- `POST /tasks/{id}/approve`
- `POST /tasks/{id}/reject`

### Day 6 挑战题带来的新增接口方向
当需求进一步明确为“任务可以被多人协作，但只有负责人能关闭任务，管理员可以回滚状态”时，现有动作集确实会被推向更多动作与更复杂关系设计。

但在继续推演后，当前更适合 V0 的接口收缩方向是：
- 保留并强化当前最小闭环：
  - `POST /tasks/{id}/assign`
  - `POST /tasks/{id}/start`
  - `POST /tasks/{id}/submit`
  - `POST /tasks/{id}/approve`
  - `POST /tasks/{id}/reject`
  - `POST /tasks/{id}/close`
- 增补一个更清晰的纠错动作：
  - 撤销 `approve`（如 `unapprove` / `revoke-approval`）
- 暂缓进入 V0：
  - `admin rollback`
  - 多协作者成员管理接口

也就是说，Day 6 的价值不在于把所有延展需求都立刻加进接口表，而在于学会识别：哪些动作属于当前最小闭环，哪些更适合后续版本。

## Day 7 定稿补充（状态链与 Week 2 边界）

### 状态链定稿
Day 7 继续收束后，当前更适合 Week 2 编码蓝图的状态链是：
- `open`
- `assigned`
- `in_progress`
- `submitted`
- `approved`
- `completed`
- `cancelled`
- `deleted`

其中关键含义是：
- `approve` 不再只是口头动作，而拥有正式状态落点 `approved`
- `close` 才是把任务推进到最终完成态 `completed` 的正式收尾动作
- `reject` 定稿为 `submitted -> assigned`，而不是直接回到 `in_progress`，这样可以保留 `start` 的动作语义

### Week 2 MVP 范围收缩
Day 7 同时明确：Week 2 优先目标不是把完整用户系统一次做全，而是先打通任务闭环主链。

当前更适合的 Week 2 MVP 范围是：
- 必做：
  - 项目骨架（module / 配置 / 路由 / DB / `/health`）
  - 最小身份能力（种子用户 / 固定测试身份 / 简化登录均可）
  - Task 基础能力（创建、详情、更新 `title` / `description`、列表）
  - 核心动作：`assign / start / submit / approve / reject / close`
  - 最小记录能力：`AuditLog` + `TaskRecord(submit/reject)`
- 明确先不做：
  - 完整注册/登录系统
  - JWT 完整方案
  - 子任务
  - 多协作者关系表
  - `admin rollback`
  - 评论系统泛化
  - 附件 / 通知 / Redis / 异步任务 / 通用工作流引擎 / 复杂 RBAC

### 请求体边界（第一轮收敛）
- `assign`：需要 body，最小核心字段是 `assignee_id`
- `start`：V0 通常可先不要 body
- `submit`：需要 body，最小核心字段是 `content`
- `approve`：V0 可先不要 body
- `reject`：需要 body，最小核心字段是 `content`

### 副作用分工边界
- 动作留痕用 `AuditLog`
- 协作正文用 `TaskRecord`
- 当前更明确需要写 `TaskRecord` 的动作：`submit`、`reject`
- `assign`、`start`、`approve` 在 V0 中通常先只要求 `AuditLog`

### 整体业务动作意识
- `submit`、`reject` 是当前 V0 里最明显需要整体成功 / 整体失败的动作。
- 因为它们至少同时涉及：
  - `Task` 状态变化
  - `TaskRecord` 正文写入
  - `AuditLog` 动作留痕
- 后续进入实现阶段时，这类动作应优先作为 service 层的一致性边界来设计。

### Day 6 第一轮权限收敛
- 多人协作不等于多人同权。
- 继续推演后，当前更适合 V0 的约束是：
  - `creator = owner`
  - `admin` 不进入任务业务流转回退
  - `submit` 只由当前单一执行者触发
- 当前第一轮收敛出的关键权限规则：
  - `approve`：仅 `owner` 可执行
  - `reject`：仅 `owner` 可执行
  - `close`：仅 `owner` 可执行
  - 撤销 `approve`：仅 `owner` 可执行
- `admin rollback` 虽然可以被想象成一种例外能力，但在 V0 中更适合延后。
- 若未来真的需要多人参与，更推荐通过子任务拆分承接，而不是直接把单任务内部做成多人并发状态推进。
