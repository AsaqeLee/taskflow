# TaskFlow V0 数据模型草案（Day 3 收敛版）

> 来源：`docs/项目目标.md`
> 状态：Day 3 业务字段与关系建模已收敛；Day 4 将继续讨论可空性、枚举值、约束与更接近数据库实现的表达。

## 文档目的

这份文档用于把 TaskFlow 当前 V0 的核心对象、最小字段集与对象关系单独沉淀出来，避免它们继续埋在 PRD / 项目目标的长文档里，方便后续进入：
- 数据库 DDL 设计
- API 输入输出结构设计
- Go domain / entity 建模
- Day 4 的字段约束和枚举讨论

---

## 设计原则

- 先按业务对象和业务关系建模，再进入数据库实现细节。
- V0 优先满足可实现性与可扩展性的平衡，避免过早做过细拆分。
- `Task` 承载任务本体，`TaskRecord` 承载协作正文，`AuditLog` 承载关键动作留痕，`User` 作为基础主体对象被引用。
- 先把最小字段集收稳，再进入可空性、枚举值、索引和 DDL 设计。
- 先服务单执行者闭环，不为了未来多角色协作过早引入复杂中间关系表。

## V0 核心对象

### 1. User
用于表达系统中的基础主体，包括自然人与 Agent。

**最小字段**
- `id`
- `name`
- `type`
- `created_at`
- `updated_at`

**说明**
- `type` 在 V0 用于区分 `human` 与 `agent`。
- 创建者、执行者等不是独立对象，而是 `User` 在任务上下文中的角色。
- Day 3 先不讨论认证凭据、profile 扩展字段、组织字段。

### 2. Task
用于保存任务本体。

**最小字段**
- `id`
- `title`
- `description`
- `status`
- `creator_id`
- `assignee_id`
- `created_at`
- `updated_at`

**说明**
- `creator_id` 表达任务稳定归属。
- `assignee_id` 在 V0 用于表达当前执行者，先服务于单执行者闭环。
- Day 3 先不把 `creator_name`、`assignee_name` 这类展示信息混入任务对象，而是通过引用 `User` 表达关系。
- `parent_task_id`、`deleted_at` 等字段可作为 Day 4 继续评估是否纳入数据库化表达的扩展项，但不进入当前最小字段集。

### 3. TaskRecord
用于统一承载评论、执行说明、审核说明、驳回说明等协作正文。

**最小字段**
- `id`
- `task_id`
- `author_id`
- `type`
- `content`
- `created_at`

**说明**
- 这张对象 / 表在 V0 统一承载评论与回执类记录。
- `type` 在 V0 至少需要覆盖：
  - `comment`
  - `execution_receipt`
  - `review_receipt`
  - `rejection_receipt`
  - `failure_receipt`
- `TaskRecord` 负责承载正文内容，而不是系统动作留痕。
- Day 3 先不把回复链、富文本附件、结构化 payload 引入最小字段集。

### 4. AuditLog
用于保存系统级关键动作留痕。

**最小字段**
- `id`
- `task_id`
- `actor_id`
- `action`
- `created_at`

**说明**
- `AuditLog` 只负责记录关键动作，不承载大段协作正文。
- `action` 在 V0 可覆盖：
  - `task_created`
  - `task_assigned`
  - `task_started`
  - `task_submitted`
  - `task_approved`
  - `task_rejected`
  - `task_closed`
  - `task_cancelled`
  - `task_reopened`
  - `task_deleted`
- `from_status`、`to_status`、`metadata` 在后续很可能有价值，但 Day 3 暂不纳入最小字段集。

## V0 核心对象关系

- `Task.creator_id -> User.id`
- `Task.assignee_id -> User.id`
- `TaskRecord.task_id -> Task.id`
- `TaskRecord.author_id -> User.id`
- `AuditLog.task_id -> Task.id`
- `AuditLog.actor_id -> User.id`

**关系理解**
- `Task` 是当前 V0 的关系中心对象。
- `User` 是被多个对象共同引用的基础主体。
- `TaskRecord` 与 `AuditLog` 都围绕 `Task` 展开，但职责不同：
  - `TaskRecord` 负责协作正文
  - `AuditLog` 负责动作留痕
- Day 3 已明确应该用“关联 / 引用”表达对象关系，而不是把其他对象的展示字段直接“包含”进当前对象。

---

## 通用骨架字段 vs 对象专属字段

### 通用骨架字段
这些字段更像对象的基础骨架：
- `id`
- `created_at`
- `updated_at`（在需要更新追踪的对象中）

### 对象专属字段
这些字段才真正表达对象的业务职责：
- `Task`：`title`、`description`、`status`、`creator_id`、`assignee_id`
- `TaskRecord`：`task_id`、`author_id`、`type`、`content`
- `AuditLog`：`task_id`、`actor_id`、`action`
- `User`：`name`、`type`

---

## 当前 V0 的推荐理解

如果当前目标是“尽快跑通，同时保留未来演进空间”，推荐采用：
- `User`：统一表达自然人与 Agent 两类主体
- `Task`：承载任务本体与最基本归属 / 执行关系
- `TaskRecord`：统一承载评论与回执正文，用 `type` 区分语义
- `AuditLog`：独立保存系统级关键动作留痕

这套方案的核心是：
- 先稳住 4 个核心对象，而不是过早引入更多中间关系对象
- 不把评论 / 回执 / 审计日志塞进任务主表
- 不把对象字段和对象关系混在一起
- 先完成业务字段与关系建模，再进入数据库实现层

以下内容可以进入 Day 4 或之后继续讨论，但当前先不纳入 Day 3 最小收敛：
- 字段可空 / 非空约束

- 是否需要提前引入 `task_participants` 关系表

## Day 4 快速结论（字段约束与 V0 取舍）

### 1. 字段可空性

#### User
- `id`：非空
- `name`：非空
- `type`：非空
- `created_at`：非空
- `updated_at`：非空

#### Task
- `id`：非空
- `title`：非空
- `description`：可空
- `status`：非空
- `creator_id`：非空
- `assignee_id`：可空
- `created_at`：非空
- `updated_at`：非空

说明：
- `description` 可空，是因为第一版允许先快速创建任务，再逐步补充描述。
- `assignee_id` 可空，是因为任务在 `open` 状态下可以尚未分配执行者。

#### TaskRecord
- `id`：非空
- `task_id`：非空
- `author_id`：非空
- `type`：非空
- `content`：非空
- `created_at`：非空

#### AuditLog
- `id`：非空
- `task_id`：非空
- `actor_id`：非空
- `action`：非空
- `created_at`：非空

### 2. V0 枚举值定稿

#### Task.status
- `open`
- `assigned`
- `in_progress`
- `submitted`
- `approved`
- `completed`
- `cancelled`
- `deleted`

#### TaskRecord.type
- `comment`
- `execution_receipt`
- `review_receipt`
- `rejection_receipt`
- `failure_receipt`

#### AuditLog.action
- `task_created`
- `task_assigned`
- `task_started`
- `task_submitted`
- `task_approved`
- `task_rejected`
- `task_closed`
- `task_cancelled`
- `task_reopened`
- `task_deleted`

### 3. V0 关系表达取舍
- `creator_id` / `assignee_id` 的直接字段表达，Day 4 版本对单执行者闭环 **已经足够**。
- Day 6 的推演确实说明：一旦需求明确强调“多人协作”，问题会开始触碰 `Task` 与 `User` 的关系建模。
- 但在继续推演 `submit / approve / close / reject` 之后，当前更适合 V0 的收缩结论是：
  - **V0 先约定 `creator = owner`**
  - **V0 先不引入多人协作者关系表**
  - **V0 仍保持单执行者闭环**
  - 如果确实需要多人参与，更适合由当前执行者拆出子任务，而不是把一条任务做成多人并发执行
- 也就是说，`owner_id + 协作者关系表` 可以作为后续扩展方向保留，但不必进入当前 V0。
- `parent_task_id` 因而重新变得重要，它更适合作为后续支撑子任务协作的扩展点。
### 4. 对数据库化表达的直接影响
- `Task` 的“通用信息修改”先只开放 `title`、`description`。
- 在当前 V0 里，仍优先保持 `assignee_id`、`status` 这类单执行者闭环所需字段；它们不走通用 patch，而走专门业务接口。
- `TaskRecord` 和 `AuditLog` 都应保留独立对象 / 表，不与 `Task` 主表合并。
- 若未来真的进入“单任务内多人协作”阶段，再考虑补充正式成员关系结构；当前 V0 更推荐通过子任务拆分来承接多人参与。
